## Constraints confirmed

- **Capability and ownership boundaries:** The projection declares its narrow read dependency as `Pick<Payments, 'readPurchase'>`; commands only select, clear or refresh replaceable read state. The consumer receives a real `ReadonlyStore`, while source writers remain inside the projection. Assembly descriptors and required slots compose the reader, configuration, view, commands and renderer without financial delivery authority or a hidden service locator. See `projection.ts:1-45,86-148` and `composition.ts:15-82`.
- **Detached finite values:** The summary omits receipt/source and historical observation graphs. `structuredClone` copies the retained finite graph before Observation freezes it, including offer lines, flags, adverse identities, completion money and status interpretation. Query copies likewise prevent the store from freezing Host query objects. The existing fixture explicitly checks the Host query and borrowed read result remain mutable while the view remains frozen. See `projection.ts:47-78` and `financial.test.ts`.
- **Latest-only behavior and direct-read invalidation:** `select` synchronously replaces the visible state before committing a new request. The real upstream load lane compares its job against the source's current revision before publishing results/errors, keeps one active run and only the latest pending request, and serializes successors. The loader awaits the actual borrowed read promise and checks abortion after settlement; it does not race the physical operation against a signal. Thus a same-turn direct read cannot expose the old ready value after selection, and an obsolete read cannot publish as the newest result. See `projection.ts:100-144`, upstream `packages/observation/src/features/store/load.ts`, and `projection-lifecycle.test.ts`.
- **Lifetime and failures:** Resources signal abortion detaches subscriptions before cleanup; the load's child scope drains its physical run. Scope registration preserves normal drain-before-source-close behavior. The projection owns neither payment runtime nor pool, and its documentation requires the Host to retain both until dependent close reports complete. Read errors become a finite sanitized failed state; renderer exceptions during later deliveries are handled by real Observation reporting without unsubscribing the renderer. Initial render failures correctly fail construction and remain Host-owned cleanup work. See `composition.ts:66-79`, `projection.ts:103-123`, upstream Observation/Resources implementations and candidate lifecycle/conformance scenarios.
- **Honest rendering and authorization claims:** The README explicitly distinguishes current synchronous reads from later-task, possibly coalesced rendering; prohibits using the view for financial/authorization decisions; leaves selection authorization with the Host; and says a capability facet is not a security sandbox. It does not promise lossless notifications, continuous authority, automatic retry or cancellation that the borrowed reader does not provide.
- **Proportionate architecture:** The finite mapping, small query/state helpers and Assembly adapter have distinct responsibilities. No concrete SOLID, Clean Architecture or DRY defect justifies another layer, another module or a universal financial facade in this optional read projection.
